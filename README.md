# CRA Internal Audit Knowledge Vault MVP

## Purpose

This local-first Obsidian vault organizes **publicly available** Canada Revenue Agency (CRA) and Government of Canada material into a navigable Internal Audit learning and retrieval corpus. It supports bounded onboarding, public-case exploration, and grounded inquiry demonstrations.

It is an independent MVP, not an official CRA product, system, repository, or endorsed initiative. It contains no non-public CRA data, taxpayer information, internal documents, protected configurations, credentials, or internal audit workpapers.

## Current vault state

The local validator currently inventories **444 Markdown files**, including **289 substantive knowledge notes** and **155 infrastructure files**. It includes:

- **6 public CRA audit/evaluation case notes** in `08-Cases/`
- **18 official source notes** in `99-Sources/source-notes/`
- organization, audit, risk/control, software/data, statistics/analytics, case, bridge, governance, and navigation content
- completed organization, audit methodology, software/data, statistics/analytics, and integrated testing suites under `16-Testing/`

Counts are regenerated by the validator; see `16-Testing/Consistency/Reports/AUTOMATED_VALIDATION.md` for the current result.

## Public-source and historical boundary

- Public CRA and Government of Canada sources are the only CRA factual basis.
- General professional concepts and vault-derived navigation are explicitly labelled.
- Public audit findings are period-bound historical evidence, not proof of current CRA conditions.
- Follow-up status is unknown unless a newer public source is linked.
- Synthetic scenarios are teaching aids and never evidence of CRA operations.

Start with [[Public-Sources-Only-Notice]] and [[Grounded-Audit-Inquiry-Guidelines]] before using the vault for a demonstration or AI-style retrieval.

## Validation and maintenance

Run the local, network-free validator from the repository root:

```bash
python scripts/validate_vault.py
```

It writes machine-readable and Markdown results under `16-Testing/Consistency/Reports/` without editing substantive vault notes. Before a material repair:

1. record the issue in `16-Testing/Consistency/CONSISTENCY_REPAIR_REGISTER.md`;
2. back up a note under `16-Testing/Consistency/Backups/` if its substantive content will change;
3. preserve source URLs, content-class labels, historical framing, findings, recommendations, report dates, audit periods, and management responses unless correcting a verified error;
4. re-run the validator and update the final consistency report.

## Current limitations and future direction

The vault is MVP demonstration material only. It is not production ready and does not provide CRA approval or endorsement. Important limitations include incomplete public follow-up evidence, unavailable public internal procedures/configurations, a dated organization baseline for personnel information, and the absence of a formal retrieval runtime.

A future RAG/GraphRAG implementation should use a curated, versioned corpus; source/citation metadata; public-only access controls; evaluation sets; grounding checks; and explicit down-ranking or exclusion of `16-Testing/**` from doctrine retrieval.
